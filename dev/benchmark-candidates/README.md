# Benchmark-candidate strategy

`kwcoco_detector_kit` is both a detector-training package and a useful source of small, realistic engineering benchmark problems. Every time an agent-generated patch fails in a way that required project context to diagnose, capture a benchmark candidate before the details fade.

The goal is not to record trivia. A good candidate tests whether another model can preserve an engineering invariant while doing the original task, ideally before seeing the compiler error or test failure that exposed the mistake.

## Workflow

1. **Fix the project first.** The benchmark candidate should be grounded in a real repair, not a speculative lesson.
2. **Save the failure evidence.** Keep the exact traceback / test output / runtime error in the conversation or journal so the repair can be audited later.
3. **Reconstruct the pre-error context.** Ask: what information was available to the agent when it made the mistake? The benchmark should usually start from that context, not from the final error.
4. **Distil the invariant.** Convert the mistake into a compact rule, e.g. "DEIMv2 HGNetv2 hybrid encoders pre-bake `eval_spatial_size`-sized positional embeddings; multi-scale collate without `supports_dynamic_input` produces tensor-shape mismatches mid-encoder" or "YAML generated by string templating must be parse-validated before launching the trainer."
5. **Write a hard question.** Include enough surrounding code shape that a model must reason about kwcoco, pytorch, ONNX, multi-GPU, or detector training; avoid giving away the answer in the prompt.
6. **Write the expected answer and validation.** Include the minimal code-shape change and the command/test that should catch the bug.
7. **Tag future dimensions.** Useful tags include `kwcoco`, `onnx-export`, `torch-multiprocessing`, `yaml-config-gen`, `multi-gpu`, `mining`, `multiscale`, `multispectral`, `webdataset`, `env-bootstrap`.

## Candidate quality bar

A candidate is worth keeping when it has all of these properties:

- **Realistic**: it came from an actual `kwcoco_detector_kit` maintenance task.
- **Contextual**: a generic StackOverflow answer is not enough; the model must preserve a project-specific invariant or API surface.
- **Minimal enough**: unnecessary files are removed, but the prompt still has enough context that the original mistake is tempting.
- **Checkable**: there is a test/run/static command or a precise expected patch shape.
- **Non-leaky**: the question can be asked without saying "the runtime says X" unless the benchmark is explicitly an error-repair task.

## Prompt levels

For each significant issue, prefer writing at least one candidate at the highest level that still feels fair:

- **Level A: pre-error operation.** "Generate a DEIMv2 training config that enables multi-scale collate for a variant whose encoder pre-bakes positional embeddings." The agent must recognise the contradiction before any error fires. This is the hardest and best test of planning.
- **Level B: error repair.** Provide the traceback and ask for the fix. Useful for debugging ability, less predictive of avoiding the bug.
- **Level C: distilled micro-question.** A tiny code example that captures the rule (e.g. "what does `yaml.safe_load` produce for this two-space-indented `collate_fn` key under `dataset`?"). Useful for focused unit benchmarks; less project-specific.

The main `pipeline-bootstrap-questions.md` file should favor Level A/B candidates with an "Expected answer" section.

## Example distillation pattern

Raw issue:

> The first DEIMv2-N training cell crashed at epoch 0 with `RuntimeError: The size of tensor a (121) must match the size of tensor b (100) at non-singleton dimension 1` deep inside `with_pos_embed`. We had overridden `eval_spatial_size: [320, 320]` but inherited the upstream `Resize: [640, 640]` in both train + val dataloaders, AND enabled `multiscale` collate. The encoder pre-baked pos_embed at 320 but the actual feature maps were 20×20 (from 640 input) or jittered to 11×11 (from multi-scale).

Benchmark distillation:

> You are generating a DEIMv2 training config for a kwcoco dataset. The user requests `eval_spatial_size=[320,320]` and `train_policy=multiscale`. The chosen variant uses an HGNetv2 hybrid encoder. What invariants must your generated YAML satisfy, and which of the user's two requests is in tension with the architecture choice? Show the minimal config that compiles, the additional fields you must populate (and why), and the static check you would run on the generated config before launching.

The hard part is preserved: the agent must recognise the encoder-architecture constraint, must enforce the all-five-sizes invariant (`eval_spatial_size = train Resize = val Resize = collate base_size = Mosaic output_size`), and must produce a structural test on the generated YAML.

## Additional benchmark dimensions specific to this kit

- **Cross-library install-order invariants.** `torch.onnx.export` on torch ≥ 2.5 imports `onnxscript` at function-call time, even when `dynamo=False`. Setup-time probes must install `onnxscript` before any export call. The same shape applies to `faster_coco_eval`, `calflops`, `tensorboard` for DEIMv2's trainer.
- **Bash-heredoc-templated YAML is fragile.** Indent arithmetic in nested heredocs has produced silent structural bugs (sibling keys becoming children, fields landing under the wrong parent). The kit's reaction is "port YAML-gen to Python and round-trip-test it" — but the underlying lesson generalises: any structured-config generation by string templating needs a parse-validate step.
- **Per-`(variant, input_size)` memory tables.** A flat per-variant batch default OOMs at large input sizes. The kit's lookup is two-dimensional. Future contributors will reach for the flat default; the question must catch them.
- **HGNetv2 vs DINOv3 input-shape contracts.** Trainer plugins must expose `supports_dynamic_input(variant)` honestly. The round-loop driver MUST coerce `multiscale → fixed` when False.

When writing questions for these classes, prefer the pre-error operation prompt. Then include an error-repair variant only as a secondary Level B prompt.

## Beyond single-issue questions: compositions

Real engineering puts several invariants in flight at once. A single-issue question tests whether an agent can preserve one named invariant. A **compositional** question tests whether the agent can enumerate the invariants from the shape of the task, hold several in working memory while drafting one patch, and detect cases where the invariants interfere.

Compositional candidates live in `compositions.md`. Each composition cross-references the component single-issue questions it builds on, along with the source commit(s) that motivate it. A composition is worth keeping when its score on a model is *not* fully predicted by that model's score on the components — otherwise it's just a stand-in for the worst component.
